# credd-bot-ts

> Tài liệu lịch sử trước khi triển khai gameflow. Các giới hạn, stack SQLite
> và lệnh chạy bên dưới có thể đã cũ. Xem [README hiện tại](../README.md).

RPG Discord bot — rewrite của `credd-bot` sang TypeScript, drizzle-orm/SQLite,
OOP + design pattern rõ ràng. Đây là bản **scaffold (M0 + phần đầu M1)**, không
phải bản port đầy đủ 100% tính năng — xem lộ trình bên dưới.

## Stack

- discord.js v14 + TypeScript strict mode
- drizzle-orm + better-sqlite3 (sync driver — hợp với combat turn-based)
- zod cho validate env
- pino cho logging
- vitest cho test

## Kiến trúc & Design Pattern

| Pattern | Ở đâu | Vì sao |
|---|---|---|
| **Command** | `core/ICommand.ts`, mỗi file trong `commands/**` | Mỗi slash command là 1 class tự chứa `data` + `execute`, tránh if/else khổng lồ theo tên lệnh |
| **Singleton** | `core/CommandRegistry.ts`, `core/EventBus.ts`, `db/client.ts` | Một instance duy nhất cho registry lệnh, event bus, kết nối DB |
| **Repository** | `repositories/**` | Toàn bộ query drizzle bị giấu sau các method có nghĩa nghiệp vụ (`findById`, `createNew`...); domain/service không bao giờ import `db` trực tiếp |
| **Facade** | `services/**` | Command layer chỉ gọi 1-2 method cấp cao, không tự orchestrate repository + event bus |
| **Observer** | `core/EventBus.ts` | Quest/achievement/vote-reward sẽ lắng nghe sự kiện (`battle.won`, `currency.earned`...) thay vì bị gọi trực tiếp từ combat code — đây là điểm original `battleEngine.js` (2527 dòng) làm sai |
| **Strategy** | `domain/combat/classes/*Strategy.ts` (raid), `domain/casino/games/*Game.ts` (casino) | Mỗi class chiến đấu / mỗi game casino 1-lượt implement chung 1 interface, dispatch qua registry thay vì if/else |
| **Factory** | `ClassStrategyRegistry.ts` (đã dùng), `DeityFactory`/`WeaponFactory` (kế hoạch) | Tạo/tra cứu Strategy hoặc entity RPG từ config mà engine không cần biết class cụ thể |
| **Decorator** | `domain/combat/RuneStrategyDecorator.ts` | Bọc thêm hiệu ứng rune combat-hook lên bất kỳ `IClassStrategy` nào (chain được), không sửa 5 class Strategy gốc |
| *(kế hoạch)* State | Battle lifecycle | Ongoing → Resolved → Rewarded thay vì boolean flags rải rác |

Đã dùng thêm ở M1: mỗi use-case nhiều-bảng (register, create character, daily
claim) chạy trong `db.transaction()` (đồng bộ, đúng bản chất better-sqlite3),
với Repository nhận `Executor` (là `db` hoặc `tx`) thay vì tự mở kết nối —
nên cùng 1 method repository dùng được cả trong lẫn ngoài transaction.

## Database

`src/db/schema.ts` được **generate tự động** từ `scripts/schema.sql` (pg_dump
thật của project gốc, 57 bảng) bằng script parser riêng, sau đó review lại thủ
công một số bảng lõi (`user_character`, `users`, `users_bag`, `user_presets`,
`user_deities`, `user_weapons`...).

### Cần review thêm trước khi dùng production

0. **`schema.sql` KHÔNG khớp hoàn toàn với `migrations/`** — đã phát hiện và
   vá thủ công: `schema.sql` thiếu 6 cột mà các migration đã thêm
   (`user_character.lifetime_exp`, `user_deities.{sigils,ascended}`,
   `users_bag.{change_class,diamond_chest,genesis_chest}`). Đã merge vào
   `schema.ts`. Nếu bạn có `pg_dump --schema-only` mới hơn từ DB thật, nên
   regenerate lại để chắc chắn không còn cột lệch nào khác — quy trình so
   sánh nằm ở `../convert/` (không nằm trong project này, thuộc phiên làm
   việc).
1. **CHECK constraint dạng `ANY(ARRAY[...])`** (ví dụ `class` chỉ nhận 5 giá
   trị, `active_preset_slot` chỉ 1|2) hiện chỉ được giữ lại **dưới dạng
   comment** phía trên mỗi bảng trong `schema.ts` — SQLite hỗ trợ CHECK nhưng
   cú pháp Postgres `= ANY(ARRAY[...])` cần viết lại thành `IN (...)`. Nên
   enforce ở tầng service (zod) thay vì chỉ dựa vào DB.
2. **Composite/multi-column FK** không được sinh `.references()` tự động
   (chỉ ghi chú bằng comment `/* FK -> table.column */`) — cần bổ sung thủ
   công bằng `foreignKey({...})` của drizzle nếu cần ràng buộc cứng ở tầng DB.
3. **`GENERATED BY DEFAULT AS IDENTITY`** (`user_presets.id`, `supporter_grants.id`...)
   được map thành `integer().primaryKey()` — cần thêm
   `{ autoIncrement: true }` nếu muốn giữ đúng hành vi tự tăng.
4. **`timestamp with time zone`** map sang `integer(mode:'timestamp')` (unix
   epoch). **`date`** map sang `text()` (chuỗi ISO). Kiểm tra lại các cột
   dùng để so sánh ngày (`reputation_exp_reset_date`, `last_daily_claim_date`)
   khi viết business logic.
5. Regenerate lại nếu schema gốc thay đổi: script parser nằm ở
   `../convert/parse_schema.py` + `../convert/gen_drizzle.py` (không nằm
   trong project này, thuộc phiên làm việc — xin file schema.sql mới nếu cần
   tái tạo).

## Đơn giản hoá UX so với bản gốc (M1)

Bản gốc dùng flow prefix-command + button (register: lore → nút "I Understand"
→ confirm; create: chọn class bằng nút → xem preview card canvas → xác nhận).
Scaffold này dùng slash command trực tiếp (`/register` chạy luôn,
`/create class:<Swordsman|...>` nhận class qua option) — **cùng logic
transaction/DB, khác lớp trình bày**. Portrait/preview card canvas thuộc M2.
Cosmetic auto-grant/equip khi tạo nhân vật (class battle skin) chưa port, để
dành cho M7 (cosmetics).

## Đợt vá "làm hết M1-M5" — bug đã tìm thấy và sửa

1. **Gear hoàn toàn không ảnh hưởng combat** (lỗ hổng lớn nhất): trước đợt
   vá này, `/raid` chỉ dùng `computeClassStats` — dù M5 cho gắn rune vào
   gear, bản thân ATK/DEF/HP của vũ khí/giáp/deity KHÔNG được cộng vào.
   Đã thêm `services/StatAssemblyService.ts`, port (rút gọn) từ
   `engine/statAssembly.js`:
   `HP=class+armor+deity`, `ATK=class+weapon+deity`, `DEF=class+armor+deity`,
   `CRIT=class+weapon` (không cộng deity), rune stat-% cộng dồn rồi nhân 1
   lần. **Chưa port:** pantheon slot 2/3 + resonance (deity phụ ăn 50%
   trọng số), `bonus_dmg_pct` theo tier vũ khí, blessing.
2. **Bug tính stat rune sai** (do chính tôi viết ở M5): code cũ nhân từng
   rune tuần tự (`atk = atk * (1+r1%) * (1+r2%) * ...` — compound), đúng
   ra phải cộng % lại rồi nhân 1 lần (`atk = atk * (1 + (r1%+r2%))`). Đã
   sửa trong `StatAssemblyService`.
3. **Bug công thức mob theo cấp**: `MonsterRepository` cũ dùng
   `base + perLevel*(level-1)`, đúng ra là `base + perLevel*level` (mob
   không trừ 1 như class). Đã sửa.
4. **Deity stat sai hoàn toàn kể từ khi có hệ Sigil**: `DeityRepository`
   cũ lưu tĩnh `curr_atk/hp/def = base` lúc pull (100% ngay từ đầu) — sai
   với hệ Sigil thật (deity mới pull chỉ có 50% base, tăng dần +5%/sigil,
   tính **tại thời điểm đọc**, không lưu tĩnh). Đã sửa `findUserDeityCurrStats`
   để join `deity_roster` và gọi `computeSigilStats` mỗi lần đọc.
5. **`/socket` dùng sai "nguồn sự thật"**: bản M5 đầu chỉ dựa vào
   `user_runes.socketed_into`, không kiểm tra số slot hay lane. Đã viết
   lại theo đúng bản gốc: đọc/ghi `native_sockets` JSON trên chính gear,
   validate lane (vũ khí native=offense, giáp native=defense) và slot còn
   trống, tự động tháo rune khỏi vị trí cũ nếu gắn sang chỗ khác.

## M3 — Combat engine: phạm vi & giới hạn đã biết

`engine/battleEngine.js` gốc là 1 hàm `resolveBattle` ~1860 dòng xử lý luôn cả
weapon/armor passive, deity blessing, rune, và cơ chế riêng của từng boss
(Bakunawa moon threshold, Fenrir phase, Aegis petrify...). Milestone này port
**đúng phần lõi 5 class passive + công thức sát thương chung**, dùng cho
**raid** (1v1 người chơi vs mob thường). Kiến trúc:

- `domain/combat/DamageCalculator.ts` — công thức thuần từ `config/combat.js`
  (mitigation DEF/(DEF+200), variance 0.9–1.1, crit ×2, `hitMultiplier`)
- `domain/combat/IClassStrategy.ts` + `classes/*Strategy.ts` — **Strategy
  pattern**: 1 class/1 file, hook `prepareOutgoingHit` / `prepareIncomingHit`
  / `onHitLanded` / `onRoundEnd` thay vì if/else chồng chéo như bản gốc
- `ClassStrategyRegistry.ts` — **Factory**: map `CombatClass -> Strategy`
- `BattleEngine.ts` — vòng lặp round, áp status effect, gọi strategy đúng hook

**Chưa port (để dành milestone sau, phụ thuộc hệ thống item/rune/deity):**
weapon/armor/deity/rune passive, cơ chế riêng từng boss, sudden-death sau
round 30, luật duel/ranked (đấu người-người thay vì người-mob), elite mob
loot, per-level reward grants (`grantLevelRewards.js`), quest progress (đã
emit event qua EventBus, chưa có subscriber). `computeClassStats`
(display-only, không cộng gear) được dùng tạm làm stat chiến đấu — thay bằng
`statAssembly.js` khi port hệ thống gear.

**Đơn giản hoá đã biết:** thứ tự hành động cố định [player, enemy] mỗi round
(bản gốc phức tạp hơn ở việc "một debuff áp dụng trong round này có che phủ
round đó hay không" tuỳ theo nó được áp trước/sau lượt đánh) — 1 Stun áp giữa
round có thể chặn luôn lượt còn lại của round đó thay vì chỉ round kế tiếp.

## M5 — Item/Rune/Enhancement: phạm vi & giới hạn đã biết

**Enhancement (`/enhance`)** — port đầy đủ bảng boost/cost/success-rate từ
`engine/enhancement.js`, đúng luật "Credux bị trừ dù thành công hay thất bại".

**Rune combat integration** — đây là chỗ **Decorator pattern** thật sự có
tác dụng: `RuneStrategyDecorator` (`domain/combat/RuneStrategyDecorator.ts`)
bọc quanh bất kỳ `IClassStrategy` nào (kể cả 1 decorator khác — chain được)
và cộng thêm đúng 1 hiệu ứng rune combat-hook (`vampiric/piercing/venom/
blight/thorns/warding/aegis_rune`), mà 5 class Strategy ở M3 **không cần
biết rune tồn tại**. Nhóm stat-% (`sharpness/precision/vitality/bulwark`)
không cần decorator — cộng thẳng vào stat khi dựng `CombatantState`
(`RaidService.applyStatRune`), đúng như cách bản gốc tách 2 nhóm này.
`BattleEngine`/`KnightStrategy` được mở rộng thêm 1 hook (`onDamageTaken`,
cho Thorns) và 2 debuff tag mới (`venom`, `blight`) — không sửa logic 5
class cũ.

**Đơn giản hoá đã biết (`RuneRepository`, `SocketService`):**
- Bỏ qua kiểm tra số lượng socket slot và "lane" (native/opposite) —
  `/socket equip` chỉ kiểm tra rune và gear có thuộc về người chơi, chưa
  kiểm tra còn chỗ trống hay đúng loại socket không.
- Chưa port: mở khoá socket (`socket_unlock_cost`), rune bag (lb/gb/db),
  essence shop/exchange, bán rune (`RUNE_SELL_PRICE`) — đây là hệ kinh tế
  rune, tách khỏi phần combat-hook đã port.
- Gear (vũ khí/giáp) đang trang bị chưa cộng ATK/DEF/HP riêng vào combat
  stat (vẫn là giới hạn đã ghi ở M3 — chờ `statAssembly.js`); M5 chỉ đọc
  **rune socket trên gear đó**, không đọc stat của gear.

## M6 — Casino: ranh giới "bắt buộc phải đọc source" vs "AI nào cũng làm được"

Cố ý chia theo đúng tiêu chí đó:

**Đã port (đọc source gốc mới biết đúng số liệu/luật, nên đây là phần
"bắt buộc"):**
- `config/casinoPayouts.ts` — MAX_BET, EVEN_MONEY, `SLOT_LADDER` (đúng 5
  mức xác suất/multiplier), công thức `crashChance`/`crashMultiplier`
- `domain/casino/CardDeck.ts` — bộ bài 52 lá dùng chung 1 deck/ván (fix
  v4.7: không trùng lá trong 1 tay), điểm baccarat/blackjack
- `domain/casino/games/{CoinToss,DiceRoll,SlotMachine,Baccarat}Game.ts` —
  **Strategy pattern**, kể cả đúng ma trận rút bài thứ 3 của Banker trong
  baccarat (so bTwo với điểm lá thứ 3 của Player)
- `domain/casino/{BlackjackSession,CrashSession}.ts` — engine thuần
  (state machine hit/stand, push/cash-out), đúng luật "Credux bị trừ dù
  thắng/thua/push" và "dealer đứng ở soft 17"
- `CasinoRepository`/`CasinoService` — transaction trừ cược + cộng
  payout + ghi `casino_logs`, atomic

**Cố ý CHƯA làm (không cần đọc source gốc, chỉ là Discord.js/canvas
thuần):**
- Render ảnh casino (`casinoCanvas.js`, `casinoRender.js`, `imagePad.js`
  — ~1100 dòng vẽ canvas): dùng text/embed thay thế trong `/casino`.
- UI nút bấm Hit/Stand cho Blackjack và Push/Cash Out cho Crash — đây là
  session Map + button collector + timer 60s, một pattern Discord.js
  thuần tuý không phụ thuộc business logic của game. Engine
  (`BlackjackSession`/`CrashSession`) đã sẵn sàng, chỉ cần 1 command mới
  gọi vào chúng.
- `betGuard.js`/`sessionStore.js` gốc (giới hạn cược theo thời gian,
  session lock chống double-submit) — hạ tầng chung, không đặc thù game.
